## 1. 이 모드는 무엇이고, 무엇을 *선언*하는가

```
vita design.sv                  # 기본: 이벤트구동 · iverilog 패리티 · 사인오프급
vita --mode=cycle design.sv     # 사이클: 조합 cone 을 원자적으로 정착시킴을 선언
```

**선언 문구(초안)**

> 사이클 모드에서 조합 cone 은 **원자적으로 정착한다.** 어떤 프로세스가 cone 의 출력을,
> 그 cone 의 입력이 바뀐 것과 **같은 델타에서** 샘플링하면, 기본 모드가 주는 *부분 전파된*
> 중간값이 아니라 **완전히 정착한 값**을 본다. IEEE 1800 §4는 region 내 프로세스 순서를
> implementation-defined 로 두므로 두 결과 모두 적법하다. 기본 모드는 iverilog 순서에
> 핀되어 있고, 사이클 모드는 그렇지 않다.

이 한 문단이 이 설계의 전부다. 나머지는 그 선언을 지키는 기계다.

## 2. 왜 막혀 있지 않은가 — 선언된 것 ≠ 조용한 것

2026-08-01 에 조합 프로세스 융합을 구현했고, 측정했고, 코퍼스 게이트까지 걸었고, **되돌렸다**
(ROADMAP §5 · `a_comb_chain_output_is_sampled_mid_propagation`). 되돌린 이유는 순서를 바꿔서가
**아니라**, iverilog 패리티를 약속한 모드 안에서 **조용히** 바꿨기 때문이다.

| | 되돌린 융합 | 사이클 모드 |
|---|---|---|
| 하는 일 | 조합 cone 을 한 활성에 정착 | **동일** |
| 약속 | iverilog 바이트 동일 | cone 원자 정착 |
| 사용자가 아는가 | ❌ | ✅ 모드 이름·문서·`-v` 에코 |
| 사다리 위치 | **silent-wrong** | **correct-support**(다른 계약에 대해) |

Verilator 가 정확히 이 거래를 하고 아무도 버그라 부르지 않는다 — **광고했기 때문이다.**

## 3. 두 가지 형태 — 3b 를 권한다

### 3a. 완전 사이클 엔진 (Verilator 정공법)
DUT·TB 모두 사이클 기반. 델타 없음, 인트라사이클 스케줄링 없음. 최대 가속이지만 **TB 의미론을
새로 정의**해야 하고(`#delay`·`fork`·SVA 의 처리) 엔진이 두 개가 된다. **XL, 다세션.**

### 3b. 하이브리드 — 이벤트 커널 유지, 조합 cone 만 원자 정착 ✅ 권장
시간·TB·리전 스케줄러는 **그대로**. 조합 cone 만 랭크 순으로 한 번에 정착시킨다.

- 엔진 1개. 커널·4-state·word화·VCD·OBS rail 전부 공유
- 되돌린 융합이 **정확히 이것이다** → 구현이 이미 존재
- 의미 차이가 **한 문장**으로 서술 가능(§1) → 검출기를 쓸 수 있다
- TB 는 이벤트구동 그대로라 `#delay`/`fork`/SVA 재정의 불필요

아래는 전부 3b 기준이다.

## 5. 진짜 신규 작업 — hazard 검출기 (이 설계의 값어치 전부)

선언만 하고 끝내면 "사용자가 자기 설계가 영향권인지 모른다"가 남는다. 그건 correct-or-loud 를
모드 밖으로 밀어낸 것에 불과하다. **사이클 모드는 자기가 달라질 설계를 스스로 말해야 한다.**

### 검출 대상
> 조합 cone 의 **출력**을 읽는 프로세스가, 그 cone 의 **입력**이 바뀌는 것과 **같은 배치에서**
> 활성화될 수 있는가?

정적으로는 과대근사(over-approximation)로 충분하다 — 놓치는 것(under-detect)이 silent 를
만들지, 과잉 경고는 안전하다.

```
후보 = { (cone C, 독자 P) :
          P 가 C.출력을 level 또는 edge 로 읽고,
          P 의 wake 원인 net 이 C 의 입력 net 과 같은 델타에 바뀔 수 있다 }
```

가장 흔한 실제 형태가 **flop 이 cone 출력을 샘플링하고 클럭과 cone 입력이 같은 활성에서
움직이는 것** — §2 의 반례가 정확히 그것이다.

### 출력
- 후보 0 → `note: 사이클 모드가 기본 모드와 동일한 결과를 냅니다` (**대다수 설계**)
- 후보 ≥1 → `warning[VITA-Wxxxx]`: 영향받는 cone·독자 프로세스의 **계층 경로를 나열**
- `-Werror` 로 승격 가능 → CI 에서 "사이클 모드로 안전한 설계만" 강제 가능

이게 있으면 사이클 모드는 **"조용히 다름"이 아니라 "다를 수 있는 곳을 지목함"** 이 되고,
사다리에서 loud 자리를 지킨다.

## 6. 그래도 걸 수 있는 게이트

계약이 다르다고 검증이 사라지지 않는다. **다음은 전부 그대로 유효하다.**

| 게이트 | 사이클 모드에서 |
|---|---|
| P5 백엔드 등가 (`backend_equiv`) | ✅ interp/VM 은 모드와 직교 — 그대로 |
| **모드 등가 (검출기 후보 0 설계 한정)** | ✅ **신규.** 후보 0 이면 두 모드가 **바이트 동일**해야 한다 — 강한 게이트 |
| iverilog 차분 | ✅ 후보 0 설계에서는 그대로 유효 |
| 결정성 (3-OS 바이트동일) | ✅ 무관 — 랭크는 `SimIr` 의 결정적 함수 |
| SchemaHash / format_version | ✅ 무영향 — 모드는 `SimOpts` out-of-band |

**핵심**: "검출기 후보 0 ⇒ 두 모드 바이트 동일"은 검출기의 **완전성을 검증하는 게이트**이기도
하다. 검출기가 놓친 hazard 가 있으면 이 게이트가 붉어진다. 검출기와 게이트가 서로를 검증한다.

## 7. 얻는 것 — 실측 기반 (과장 금지)

되돌린 융합에서 잰 값 그대로다:

| shape | d | interp off→on | +VM off→on |
|---|---|---|---|
| in-module | 48 | 73.1 → 42.2 (**1.73×**) | 49.4 → 19.8 (**2.50×**) |
| instances | 48 | 145.5 → 73.0 (**1.99×**) | 121.2 → 51.8 (**2.34×**) |
| examples 4종 | 2–5 proc | **1.00×** (조합 사슬 없음) | 1.00× |

**얕은 설계엔 0 이다.** 이 모드는 깊은 조합 cone 을 가진 설계 전용이고, 그런 설계가 실수요로
있는지는 §8 이 답한다.

그리고 **천장이 따로 있다**: 융합 후에도 실 RTL 형태는 `total 52.8 / vm 17.5 / fallback 1.2`
→ **엔진이 64.6%**(넷 부기·propagate·NBA). 사이클 모드는 그걸 안 건드린다. 더 가려면 **넷 개수
축소**가 필요하고 그건 G2 관찰성과 충돌한다 — 단 모드별 스코프가 가능하다(§10).

## 8. 선결 측정 — 미충족 시 착수 금지

이번 세션이 여섯 번 증명했다: **가정한 payoff 위에 기계를 지으면 매번 틀린다**
(C +0.2% · D 1.00× · F 1.06× · E 값 발산).

| # | 측정 | 통과 기준 |
|---|---|---|
| M1 | **실 대형 RTL 한 개**에서 `comb_ranks().max()` = 조합 깊이 | 깊이 ≥ 6 인 cone 이 실재 |
| M2 | 그 설계에서 `f`(적격 바디 wall-clock 몫) | 융합 시 f 가 유의미하게 상승 |
| M3 | 그 설계에서 hazard 검출기 후보 수 | 0 이거나 소수 — 다수면 모드의 값이 없다 |

**M1~M3 은 전부 기존 계기로 잰다**(`comb_ranks` 공개 API · G0 스크래치 타이머 · 검출기 프로토타입).
설계 하나 구하는 것 외에 신규 코드 불필요. **반나절.**

> 지금까지 측정은 전부 합성 체인과 2–5 프로세스 예제였다. 대형 설계는 프로세스/넷 비율이
> 달라 **64.6% 라는 숫자가 완전히 다를 수 있다.** 그 숫자가 이 모드의 천장을 정한다.

## 9. 공수·위험

| 단계 | 규모 | 비고 |
|---|---|---|
| M1–M3 선결 측정 | **XS** (반나절) | 신규 코드 ~0 |
| 융합 되살리기 (`git revert` 의 revert) | **S** | 코드 존재 · 2건의 디버그도 이미 기록됨 |
| **hazard 검출기** | **M** | 이 설계의 실질 신규분 |
| 모드 배선 (`--mode=cycle` · `-v` 에코 · staged 통과) | **S** | `--backend` 선례 그대로 |
| 모드-등가 게이트 + 검출기 완전성 게이트 | **S** | `backend_equiv` 구조 재사용 |
| 문서 (모드 계약·한계·매뉴얼) | **S** | |
| **합계** | **~3–4 세션** | 3a(완전 사이클 엔진)는 XL·다세션 |

**최대 위험 = 검출기의 under-detection.** 놓친 hazard 는 사용자가 선언을 읽고도 예상 못 한
발산을 만난다는 뜻이다. 완화 = §6 의 상호 검증 게이트 + 과대근사 설계(의심스러우면 경고).

## 10. 열린 결정 사항 (오너 판정 필요)

1. **모드를 만들 것인가** — M1–M3 통과가 전제. 통과해도 "엔진 표면이 2개가 된다"는 유지비는 남는다.
2. **검출기 후보 ≥1 일 때 기본 동작** — warning 인가, `-Werror` 기본인가, 아예 거부인가.
   correct-or-loud 정신에는 **거부(옵트아웃 플래그 제공)** 가 가장 가깝다.
3. **G2 관찰성을 모드별로 스코프할 것인가** — 사이클 모드에서 `--probe`/계층 VCD 를 축소 허용하면
   넷 개수 축소(§7 천장)까지 열린다. 열지 않으면 천장은 그대로.
4. **`--mode=cycle` 이 `--backend vm` 과 직교인가** — 직교로 두는 것을 권한다(측정상 곱해진다:
   1.99× × VM = 2.34×).

## 11. 재진입 트리거

**M1–M3 전부 통과 + 오너가 §10.1 을 승인**. 하나라도 미충족이면 이 문서는 기록으로만 남는다.

## 12. 배운 것 (이 스케치가 서 있는 근거)

- **선언되지 않은 의미 변경은 silent-wrong, 선언된 것은 다른 계약**이다. 되돌린 융합과 이 모드의
  코드는 같고 사다리 위치는 정반대다.
- **게이트는 그 안에 든 형태만큼만 강하다.** 코퍼스 전 설계가 `#1 clk=1` 형태라 융합 버그를
  못 잡았다. 새 모드의 게이트는 **반례 형태를 먼저 코퍼스에 넣고** 시작해야 한다.
- **실패한 작업이 부품을 남긴다.** `comb_ranks` 는 1.00× 로 기각된 levelize 의 유산인데, 이
  설계의 스케줄링 원시연산이다.
